# Capacitor → React Native 전환 검토

2026-09-25 · 검토 중. 근거 칸(⬜)을 채운 뒤 결정한다.

8/16 [Capacitor 선택](capacitor_선택.md)의 후속이다. 공모전 제출이 끝나 일정 제약이 없어졌다.

---

## 전제

| 항목 | 값 |
|---|---|
| 웹 | 유지하지 않는다. 앱 한 벌만 남긴다 |
| 후보 | React Native(Expo)만 본다. Flutter는 Dart라 재사용이 0이다 |
| 서버 | `src/app/api/*`는 Vercel에 그대로 둔다. 앱은 지금처럼 절대 주소로 부른다 |
| 현재 네이티브 기능 | 없음. Capacitor 플러그인을 쓰지 않는다 |

네이티브 기능이 필요하다는 것만으로는 전환 근거가 되지 않는다. Capacitor도 위치·푸시·진동·카메라를 플러그인으로 쓸 수 있다. 차이는 **화면을 그리는 방식**(WebView vs 네이티브 뷰)과 **앱이 꺼져 있을 때 도는 작업**에서 난다.

---

## 논리

### ① 앞으로 만들 핵심 기능이 WebView가 약한 영역이다

F5 현장 실시간 안내의 근접 알림은 앱이 꺼져 있어도 위치를 받아야 한다. 백그라운드 위치는 Capacitor에서 커뮤니티 플러그인에 기대야 한다.

| 근거 | 상태 |
|---|---|
| 백그라운드 근접 알림을 만드는가 | ✅ 만든다 (팀 확인 참고) |
| Capacitor 백그라운드 위치 플러그인의 한계 (유지 상태, 알려진 이슈) | ⬜ |
| RN 쪽 대안 라이브러리와 성숙도 | ⬜ |

> 백그라운드 위치의 **스토어 심사 리스크는 RN에서도 같다.** 8/16에 뺀 이유는 Play Store 정책(`ACCESS_BACKGROUND_LOCATION` 별도 심사)이다. 이 항목은 구현 안정성만 근거로 삼는다.

**첫 칸이 비면 ①은 성립하지 않는다.**

### ② 현장에서 쓰는 앱이라 네이티브 UI 체감이 중요하다

걸으면서 한 손으로 쓰는 앱이다. 스크롤, 화면 전환, 뒤로 가기 반응이 품질을 좌우한다.

| 근거 | 상태 |
|---|---|
| 현재 앱에서 느린 곳 (기기에서 피드 스크롤, 상세 진입 체감) | ⬜ |
| 스파이크 RN 화면과 같은 화면 비교 | ⬜ |

지금 앱이 충분히 부드러우면 ②는 ①을 받치는 보조 논거로 낮춘다.

### ②-1 iOS로 확장하면 확인할 대상이 바뀐다

iOS는 사업화 단계에서 낸다(팀 확인 참고).

| | Capacitor | RN |
|---|---|---|
| 화면을 그리는 것 | 안드로이드 크롬 엔진 · iOS 사파리 엔진(WKWebView) | 각 OS의 UI 부품 |
| 확인할 것 | 웹 호환성 (CSS·JS가 두 엔진에서 같게 동작하는지) **+** OS다운 동작(전환, 뒤로 가기, 스크롤 튕김)을 웹으로 흉내 낸 결과 | OS별 동작 차이 (OS가 기본 제공) |

RN에서도 확인할 것이 없어지지는 않는다. Capacitor는 웹 호환성과 OS다운 동작을 **둘 다 직접 맞춰야 하고**, RN은 OS다운 동작을 **기본으로 얻는다.**

| 근거 | 상태 |
|---|---|
| iOS 출시 계획이 있는가 | ✅ 사업화 단계에서 낸다 |
| 현재 CSS 중 사파리에서 다르게 동작할 항목 (`globals.css`, 애니메이션, 안전 영역) | ⬜ |
